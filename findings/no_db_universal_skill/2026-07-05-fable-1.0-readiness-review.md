## 0. Bottom line

**Neither audience is served by calling this 1.0 today, but the two gaps are different
sizes.** As a *product for real Tübingen students*, the package is close: the skill
logic is genuinely good, the honesty discipline (caveats, no invented contacts, 2e/2f
verification) is unusually strong, and the remaining gap is operational — nobody outside
the project has ever run the shipped artifact (Design-Entscheidungen.md §11 TODO 1+2,
both "Hoch/Ja", both open; the one outside tester had no protocol). As a *thesis*, the
gap is larger and is exactly the one `findings/gesamtplan-2026-07-02.md` §2 named the
"Größter Notenhebel" and then didn't close: the central scientific claim (curated
narrow scope beats plain Claude; breadth erodes the advantage) is still an assertion,
every number was produced and scored by the same agent lineage, and — my sharpest
finding below — **the two hard-faculty numbers that flipped the go/no-go to GO on
2026-07-04 are not clean blind measurements** (§3.2). The single biggest blocker for the
thesis is the unrun scope-erosion experiment (gesamtplan T3); for the product it is
distribution + a protocolled external test (TODOs 1–2). Both are feasible; neither has
started.

## 2. Q1 — The scope claim (SLLN argument)

**Is the argument sound as currently reasoned? Partially — the conclusion is probably
right, but the reasoning as written proves less than it claims.**

The formalization in `gesamtplan-2026-07-02.md` §3 Idee 6 (Δ = E[Q(Tool) − Q(Baseline)];
fixed curation capacity ⇒ broader scope ⇒ lower curation density per query ⇒ Δ→0) has
two soft spots:

1. **It conflates two different scope moves.** Adding KIT *with no backbone* obviously
   converges to baseline — but that's true by construction, not by a law-of-large-numbers
   effect (a tool whose first step is "google the entry point" *is* the baseline; the
   gesamtplan itself says this under Idee 5). Adding KIT *with* a curated backbone
   (~2 days per the gesamtplan's own T10 recipe estimate) does **not** reduce Tübingen's
   curation density at all — reference files don't dilute each other; only maintenance
   attention does, and that's a much weaker, slower effect than "Δ→0 im Erwartungswert".
   The honest form of the claim is the **dose-response** version the gesamtplan also
   states: *advantage is proportional to curated local-knowledge density in the query
   scope* — which is a defensible, testable engineering claim, not an SLLN corollary.
   The write-up should drop the SLLN framing (it lends false mathematical authority) and
   keep the density claim.

2. **The supporting data is suggestive but confounded.** The two cited internal data
   points — MPI-IS fix lifting CS 60%→100% (more local knowledge → bigger Δ) and the weak
   C1 company delta (+17pp where baseline already knows Bosch/ZF/Mercedes) — are
   consistent with the claim but each has an alternative reading (the MPI-IS fix also
   fixed a plain coverage bug; C1's weak delta partly reflects a circular GT ceiling of
   100% for the tool arm).

**Minimum experiment to make it a tested claim:** exactly gesamtplan §6 T3, and it can
be trimmed further: *one* foreign university (TUM, the harder comparison per §7 Frage 1),
*one* faculty, ~6-chair GT curated by a second person, 4 cells ({tool w/o backbone,
baseline} × already-existing Tübingen numbers reused for the in-scope cells at n=1, with
n≥2 only on the two new out-of-scope cells). That is ~2–4 working days including GT
curation. **Feasible before submission — and it is the highest-value remaining task in
the entire project.** Note the gesamtplan's own risk framing (§7): a negative result
("TUM's central portal helps tool *and* baseline") is still a reportable, defensible
finding — the experiment can't really fail, only inform.

## 3. Q2 — Evaluation methodology, read skeptically

**The current evidence supports "the mechanism works and the design is sound." It does
not yet support the strength of the aggregate claims as written ("GO", "all 6 faculties
clear 80%", "steering confirmed strong") without caveats that are currently scattered
rather than attached to the headline.** Four specific problems:

### 3.1 Single-agent authorship/scoring — acknowledged, never mitigated

Every recall, precision, steering, and robustness number was designed, executed, and
scored inside the same project lineage; several runs scored ground truth authored days
earlier by the same setup. The project *says* this plainly
(`03-hardening-and-evaluation/README.md`, scorecard §6) — the honesty is real — but the
cheap mitigation the gesamtplan prescribed (second person re-scores ~20%) was never
done. Precision is especially exposed: it is "scored by human judgment on the MAP
output" (`eval_ground_truth/README.md:65`) against the map's *own* relevance-rationale
field — i.e., the agent grades whether its own justification "holds up." The 100%
precision numbers should be treated as upper bounds until one outsider re-scores a
sample.

### 3.2 The GO-flipping numbers are not blind — this is the review's main pushback

Checking the no-peeking discipline run by run, as the briefing asked:

| Run | Claimed status | Actual status |
|---|---|---|
| Roadmap-J run 1 (CS, 100%/75%) | — | **Broken, self-flagged** (GT read before Pass 1; STATUS row admits it) |
| Task O re-run (CS, 100%/100%) | no-peeking held | Plausibly held (persona reconstructed without opening GT) — but same-session as the fix it validates |
| Task Q run 1 (Humanities, 60%) | blind | Genuinely blind — and *below bar* |
| Task T Humanities "100%" | transparent re-score | **Not a run at all** — a re-score of the old run by a session that was explicitly un-blind on Humanities (its own write-up says so) |
| Task T Law (60%) | blind | Genuinely blind — and *below bar* |
| Task U Law re-run (80%) | "blind re-run" | **Contaminated:** the Task U session necessarily read Task T's root-cause analysis, which names Remmert as the false-negative *and* names her Schwerpunkte ("Allgemeine Grundrechtslehren") — the exact fact whose discovery the re-run then credits to Pass-2 enrichment. The agent knew the answer for the one chair whose flip produced the 80%. |

So: **every genuinely blind hard-faculty measurement in this project came in at 60%**,
and both numbers in the GO table above 60% were produced with knowledge of what the
answer should be. To be fair to the project: the Humanities root-cause (lossy persona)
is convincing, the Task U fix is a real, principled rule (the Droege/Seiler
still-excluded check is good evidence it didn't just loosen the filter), and the
scorecard footnotes all of this. But the go/no-go doc's own standard — "You cannot
credit a ≥80% hard-faculty recall that no run has yet shown"
(`2026-07-03-core-done-go-no-go.md:104`) — was, on a strict reading, not met by the
evidence that flipped it. **I disagree with the unqualified GO** (see §8).

The cheap repair is sitting in the repo: `theology.md` is the one hard-faculty GT that
no eval session has ever opened mid-run. One fresh-conversation blind Theology run
(~20 min per the runbook) is the only way left to get an uncontaminated hard-faculty
data point, and it should happen before the thesis claims the robustness bar.

### 3.3 Circular company ground truth — acknowledged, unresolved, now 7 days old

Nothing to add beyond the project's own framing except urgency: the 100%-recall company
table is the *least* informative number in the scorecard, and the write-up currently
gives it equal visual weight with the university numbers. Either build the independent
GT (gesamtplan T4, ~1 day) or explicitly demote the company eval to "plumbing check"
status in the thesis text.

### 3.4 Steering: proven for the mechanism, over-claimed as "strong"

Task P is well-designed for what it tests, and the near-disjoint maps are a real result.
But two personas *engineered to be maximally inverted* on one faculty establish "the
profile *can* redirect the search," not "the interview steers typical students." The
write-up mostly says this correctly; the shorthand "steering confirmed (strong)" that
propagated into STATUS/MASTERPLAN drops the qualifier. A subtler test (two personas
sharing interests but differing only in methods + thesis style, prediction: overlapping
option sets with different *ranking and framing*) would be the next increment — desirable
for the thesis, not blocking, **provided** the claim is worded as "mechanism proven on
divergent profiles."

Also worth stating in the methods chapter: n=1 per cell throughout, no variance
estimate, on a stochastic system (the gesamtplan demanded n≥3; no run ever repeated),
and the Med/WiSo numbers date from 2026-06-28 under a skill version four fix-rounds old.

## 4. Q3 — Product readiness for real users

**The gap between "package-ready" and "a Tübingen student gets value" has three layers:**

1. **Access/installation.** The quickstart assumes the student has a capable coding
   agent, a paid plan with generous web-search quota, and knows what "copy skill folders
   into your agent's skills directory" means. That's fine for CS students (Domi's own
   Idee 6 prediction) and a real filter for everyone else. Untested assumption: a
   discovery run makes dozens of WebSearch/WebFetch calls — whether a free/low-tier
   student can complete Pass 1+2 at all is unknown.
2. **First-run experience.** Gehler's three signals were all onboarding-shaped, and
   M1–M3 plausibly address two of them — but the fixes shipped without any live
   exercise (O6) and without re-testing on Gehler or anyone else. The loop
   "feedback → fix → verify with a user" is half-closed.
3. **Nobody has run the shipped artifact.** Gehler tested a dev checkout. The release
   zip (`build_skill_release.py`, 8 skills) has never been installed cold by an
   outsider. This is the literal definition of not-yet-beta, and STATUS.md's own Phase-3
   gate said so ("beta-ready after independent live test") — that condition is still
   unmet 7 days later.

**Minimum viable path (one week of calendar time, ~2 days of effort):**
- **Channel:** Fachschaft Informatik first (named in MASTERPLAN §7, warm contact,
  matches the predicted early-adopter population), with 1–2 deliberately non-CS testers
  recruited personally (psychology or humanities — the faculties the tool claims and the
  backbone is thinnest for).
- **Protocol (1 page):** before the run, each tester writes down the 2–3 supervisor/
  company options they already know (their personal baseline). Then: install the release
  zip from written instructions only (no maintainer help — measure whether they get
  stuck), run `thesis-finder` end-to-end, save the map.
- **Measure:** (a) ≥1 credible option per tester they did not already know (the honest
  value metric — beats recall-vs-GT for external validity); (b) count of factually wrong
  statements in the map (misattributions, dead URLs — the trust metric the professor
  research said matters most); (c) did they finish without help; (d) would they contact
  one of the options (intent as proxy for usefulness). Score (a)/(b) jointly with the
  tester, which simultaneously chips at §3.1.
- This one exercise closes TODO 1, produces the qualitative-eval chapter the gesamtplan
  wanted (T9, shrunk), and is the prerequisite for TODO 2's wider distribution.

## 5. Q4 — Maintenance after handoff

**Real risk, but the design already contains its main mitigation — say so, then add the
minimal process.** Two staleness channels with different severities:

- **Runtime correctness is largely self-healing.** Because the backbone is a *routing*
  anchor, not a data source, a rotted entry degrades into either a 404 (company skill
  has a codified fallback query, `find-company-thesis-options/SKILL.md:83-85`) or a
  stale page that Pass-2's 2f existence + affiliation checks are specifically built to
  catch — and did catch, live (Oh/KAIST relocation, where the *official university page*
  was the stale artifact). This is a genuinely strong property and the thesis should
  claim it explicitly: the failure mode of backbone rot is *reduced recall*, not
  *wrong answers*.
- **Recall decay is not self-healing.** Missing new chairs/companies, renamed
  URL trees (two 404s already on record within *one week* of authoring), and section
  drift accumulate silently. The uni backbone says "Last checked 2026-06-27" —
  wholesale, once, by the author.

**Minimum viable process given zero paid maintenance:**
1. A `MAINTENANCE.md` (half a page): *when* — once a year, September, before the
   winter-semester thesis wave; *what* — run the link check, fix 404s, spot-check 5
   entries per backbone, bump `Last verified`; *time-box* — 2–3 hours; *who* — named
   person or explicitly "unowned — tool degrades gracefully, see caveat".
2. A trivial CI link-checker over the two backbone files' URLs (a 30-line script; the
   repo already has CI plumbing in `qa.yml`). This converts "unnoticed rot" into a
   red check, which is the whole battle. This is the single cheapest high-value
   engineering task left in the repo.
3. Wire the existing coverage caveat to the backbone's `Last checked` date (it already
   templates "[backbone date]" in the company skill) so a student in 2028 sees "backbone
   last verified 2026" and can calibrate trust — the honest-degradation principle
   applied to time.

TODO 5's "Mittel/Optional" rating is right *for the product today*; for the thesis, one
paragraph naming this process (even if unstaffed) turns a reviewer's "what happens in a
year?" objection into a design feature.

## 6. Q5 — Remaining coverage gaps

**Acceptable as documented limitations — with one wording fix and one cheap run.**

- **Non-MINT company coverage:** Task L did this right. The Studiengangs-Routing table
  is honest to the point of self-deprecation (Recht: 0 entries with a structural
  explanation; Sozialwissenschaften: 1; explicit "kein Firmen-Track existiert" row that
  routes theology/philosophy students away from the skill entirely). Thin-but-honest
  beats padded, and the EdTech smoke test showed the <5-candidates fallback works. **But
  the frontmatter oversells it:** `find-company-thesis-options/SKILL.md:3` says
  "across all sectors … for any discipline" — the routing table itself proves "any
  discipline" false for at least three fields. The description is the one place a
  student's agent reads *before* the honest table; align it ("most disciplines; some
  fields have no company track and are routed to university discovery").
- **Theology:** not blocking as coverage (the bar's ≥6-faculties condition doesn't need
  it) — but blocking as *methodology*, because it is the last uncontaminated hard-faculty
  GT (§3.2). Run it for the blindness repair, and get the coverage point for free. It
  also carries the known N.N.-vacancy trap, which would test the "honest no-staffed-chair"
  behavior on a real case — exactly the robustness story the thesis wants to tell.

## 7. Q6 — Findings this briefing didn't ask about

Beyond the punch-list items O1–O6 (shipped stale paper index with wrong-person
conflation; CS-only degree-program file; portability contradictions; missing link
audit; wording defects; unverified M-fixes), three structural observations:

1. **SKILL.md Step 4 duplicates the backbone table.** `find-university-chairs/SKILL.md`
   hardcodes all 8 faculty URLs that also live in `tuebingen-faculty-backbone.md` — two
   copies of stale-prone data with no single source of truth. When a URL drifts (already
   observed twice), someone must remember to fix both. Either SKILL.md should point at
   the reference (as Steps 2–7 do for search-strategy) or the duplication should be a
   documented, deliberate redundancy with a sync note.
2. **No mechanism enforces the workflow.** The 8-step process, the two-verification
   rule, and the self-check checklist are all prompt-compliance-dependent; the
   gesamtplan (§2 row 1) said to record this as a known limitation in the thesis, and
   the thesis-report currently doesn't. One paragraph ("the eval numbers implicitly
   measure compliance of one model family at one point in time; a weaker executor model
   degrades the tool in unmeasured ways") would pre-empt an obvious committee question.
3. **The eval harness's live runners are dead code for this project.** `VALID_RUNNERS`
   requires Codex (unavailable — user has Claude Pro only; see
   `gesamtplan-2026-07-02.md` §2), so the "harness" in the repo runs fixtures only, and
   every real measurement is the manual runbook. That's fine — but README.md's "Quality
   gates" section and the CI workflow name (`codex-multiturn-evals.yml`) suggest more
   automation than exists. The thesis methods section should describe the manual
   protocol as *the* instrument, not as a fallback.

## 8. Explicit disagreements with recorded conclusions

1. **The 2026-07-04 GO (`2026-07-03-core-done-go-no-go.md`).** I would have recorded
   this as **"GO, provisional — pending one uncontaminated hard-faculty run"**. The
   NO-GO analysis of 2026-07-03 was exemplary and its own standard ("you cannot credit a
   recall no run has shown") was then not strictly honored: Humanities 100% is a
   re-score by an un-blind session, and Law 80% was produced by a session that had read
   the document naming both the missed chair and the evidence that flips her (§3.2).
   The project reversed a premature GREEN once before (2026-06-28 CI incident) for
   exactly this pattern — a verdict resting on what was convenient to run rather than
   what the criterion demanded. The fix is one blind Theology run away; take it.
2. **Scorecard §1's Humanities row ("60% → 100% post-protocol-fix").** The arrow
   notation makes a re-score look like a re-run, and the GO table then cites "Humanities
   100%" without the caveat. The footnote exists but the headline number travels alone
   (it already propagated caveat-free into MASTERPLAN §8 and STATUS's banner).
3. **"Phase 4 — Hardening (DONE)" / "core is done" framing (MASTERPLAN §8).** Overstated
   while §3.1–3.3's mitigations (all named in the project's own planning doc) remain
   open. "Core validated by internal single-rater evaluation; external validation open"
   is the defensible sentence.
4. **Gesamtplan execution drift.** The gesamtplan's priority order was T1–T3 (thesis,
   protocol v2, scope experiment) above all else, with "Kein neues Feature bringt mehr
   Notenpunkte als ein verteidigbares Experiment." What actually got built since was
   T6/T7-adjacent hygiene, Task L (backbone breadth — a feature), and M1–M3 (UX
   features). All good work, all real improvements — and all lower on the project's own
   priority list than the experiment that still hasn't started. Worth naming so the
   pattern doesn't continue.
